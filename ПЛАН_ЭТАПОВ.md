# План реализации проекта «Табель» (QR-учёт рабочего времени)

Версия плана: 1.0
Дата: 2026-10-19
Основание: ТЗ «Система табелирования сотрудников», версия 1.0

Рабочая директория проекта: `/opt/compose/tabel`
Стек (зафиксирован на Этапе 0):

- Сервер: **Go 1.24** (стандартный `net/http`, pgx/v5, go-redis/v9)
- БД: PostgreSQL 16 (+ PgBouncer), Redis 7
- Хранилище: **Garage** (S3-совместимое) — вместо MinIO (MinIO изъял публичные образы)
- Обратный прокси/TLS: Nginx, порт 443 — **отложено на этап деплоя** (сейчас HTTP)
- Мобильное приложение: Flutter (Android API 26+ / iOS 15+)
- Веб (админ + оператор): React 18 + TypeScript + Vite
- Контейнеризация: Docker Compose
- Документация API: OpenAPI 3.1 (Swagger)

Правила работы: этапы выполняются последовательно. Переход к следующему этапу — только после
явного согласования. Внутри этапа все спорные решения выносятся на уточнение.

## Этап 2. Серверная часть: ядро — ✅ ВЫПОЛНЕН (2026-10-19)

Цель: рабочий каркас API и базовые сущности.

### Фактически выполнено

- **Аутентификация**: JWT HS256 (access 15m, refresh 720h, настраивается `JWT_ACCESS_TTL` /
  `JWT_REFRESH_TTL`), роли `employee` / `operator` / `admin`. Refresh-токены хранятся в
  `sessions` как SHA-256 хэш и ротируются при обновлении (старая сессия отзывается).
  При отсутствии `JWT_SECRET` ключ детерминированно выводится из `SETTINGS_ENCRYPTION_KEY`.
- **Пароли**: Argon2id (m=64 MiB, t=3, p=4), формат PHC; политика — минимум 5 символов,
  хотя бы одна буква и одна цифра.
- **Блокировка**: после 5 неудачных попыток `is_locked = true`, вход возвращает `423 Locked`
  с телефоном поддержки. Разблокировка/сброс попыток — `POST /admin/users/{id}/unblock`;
  запрет авторизации (`auth_blocked`) — `/block` и `/unblock`.
- **Регистрация по QR**: `POST /auth/register` проверяет существование и статус QR-токена,
  срок действия (Asia/Novosibirsk), активность сотрудника и подпись. Логин = телефон.
  Повторная регистрация запрещена (`409`), после `reset-registration` — разрешена и
  обновляет существующую учётную запись.
- **QR-криптография**: пакет `internal/qr` — канонический JSON, ECDSA P-256/SHA-256,
  подпись/проверка. Приватный ключ генерируется при первом обращении и хранится
  зашифрованным в SQLite настроек. Полная выдача подписанных статических/бумажных QR —
  Этап 3; в `development` допускаются токены без подписи, в `production` подпись обязательна.
- **Справочник сотрудников**: `GET/POST /admin/employees`, `GET/PATCH /admin/employees/{id}`
  (поиск, фильтр активности, пагинация, уникальность табельного номера).
- **Профиль главного администратора**: `GET/PUT /admin/profile` — email и телефон поддержки
  в SQLite-настройках. При `POST /setup/complete` можно сразу создать главного администратора
  (необязательные поля `admin_login` / `admin_password`).
- **Отметки**: `POST /mark` — валидация, обязательный `Idempotency-Key` (UUID), защита от
  повторной доставки (возврат ранее созданной отметки, `200`), дедупликация одинаковых
  событий в пределах 2 минут, INSERT в партиционированную `marks`.
  `GET /marks` — отметки текущего сотрудника с фильтром `from`/`to`/`limit`.
- **Журнал аудита**: `audit_log` + `GET /admin/audit` (фильтры action/entity/from/to,
  пагинация). Пишутся вход/выход, неудачи входа, регистрация, смена пароля, действия
  с сотрудниками/пользователями, профиль администратора, создание отметок, завершение установки.
- **Миграция `00012_auth_core.sql`**: индексы для дедупликации отметок и активных сессий,
  уникальность главного администратора.
- **Инфраструктура**: `JWT_SECRET`, `JWT_ACCESS_TTL`, `JWT_REFRESH_TTL` в `.env.example`
  и compose; поля администратора в странице установки `web-admin`.

### Проверка (фактические результаты)

- `go build ./...`, `go vet ./...`, `gofmt` — чисто.
- Unit-тесты: `internal/auth` (политика, Argon2id, JWT, срок действия, подмена, хэш токена),
  `internal/qr` (канонический JSON, подпись/проверка, сохранение ключа) — проходят.
- Интеграционный тест `TestRegistrationAndMarkE2E` на реальной PostgreSQL — проходит:
  создание администратора и сотрудника, выпуск QR, регистрация, вход, `GET /me`,
  создание отметки, повтор по Idempotency-Key, `GET /marks`, запись в аудите.
- Ручной сквозной прогон (изолированная БД + контейнер):
  `setup/save` → `setup/complete` (создан главный админ) → логин админа →
  создание сотрудника → регистрация по QR → логин сотрудника → `POST /mark` (`201`) →
  повтор с тем же ключом (`200`, тот же `id`) → новый ключ в пределах 2 минут (`200`, дедупликация) →
  `GET /marks` (1 запись) → refresh-ротация (старый refresh → `401`) →
  смена пароля → 5 неудачных входов (`423`) → unblock админом → успешный вход →
  block/unblock (`423`/`200`) → reset-registration → повторная регистрация → `check_out` (`201`).
- Проверены CORS-заголовки, неверная подпись QR (`400`), отсутствие `Idempotency-Key` (`400`),
  невалидный UUID в пути (`400`), `GET /admin/audit`.

### Отклонения и решения

- JWT реализован на стандартной библиотеке (HS256), без внешней зависимости.
- Блокировка после неудачных попыток действует до разблокировки администратором
  (автоматического разблокирования по времени в ТЗ нет).
- Создание главного администратора добавлено в мастер установки (необязательный шаг);
  это закрывает потребность Этапа 2 в администраторе для проверки API.
- В `development` разрешены QR без подписи; строгий режим включается `APP_ENV=production`.

### Не сделано (перенесено)

- `invalid_transition`, автозакрытие смены, `overtime`, геозона `outside_office` — Этап 4.
- Выдача/подпись статических QR, бумажные QR, PDF/A, массовая загрузка — Этап 3.
- Делегирование и уведомления — Этап 6; OAuth/экспорт — Этап 5.
- Полноценные веб-панели администратора и оператора — Этапы 10–11.

## Этап 3. Серверная часть: QR-подпись, массовая загрузка, бумажные токены — ✅ ВЫПОЛНЕН (2026-10-19)

Задачи:
- Генерация ключей ECDSA P-256 при развёртывании; приватный ключ только на сервере.
- Подпись/проверка QR (canonical JSON без `signature`).
- Статические QR: приём JSON, подпись при загрузке.
- Массовая загрузка JSON/архива: предпросмотр → валидация → подтверждение → отчёт (строка/причина).
- Бумажные QR-токены: выдача на 1 месяц (Asia/Novosibirsk), один активный на сотрудника, отзыв.
- Проверка бумажного QR: подпись + токен + сверка полей с БД (флаг `qr_data_mismatch`).
- Печатная форма PDF/A (логотип, QR, данные, срок, инструкция).

Результат: полный цикл QR (static + paper), массовая загрузка, PDF/A.

### Фактически выполнено

- **Ключи ECDSA P-256**: `EnsureQRKey()` вызывается при старте backend, ключ хранится
  зашифрованным в SQLite (`qr_private_key`) и переиспользуется между перезапусками;
  публичный ключ доступен в PEM.
- **Канонический JSON**: сортировка ключей, `json.Number`, исключение верхнеуровневого
  поля `signature`; подпись/проверка ECDSA P-256 + SHA-256, ASN.1 DER в base64.
  Некорректная base64-подпись считается невалидной (без 500).
- **Статические QR**: `POST /admin/qr/static`. Сервер проверяет сотрудника, сверяет
  известные поля payload, дополняет его `employee_id`, `employee_number`, `full_name`,
  `position`, `phone`, `email`, `token`, `type`, подписывает и сохраняет. Предыдущий
  активный статический токен сотрудника отзывается (ротация).
- **Массовая загрузка**: `POST /admin/qr/bulk?mode=preview|commit` с multipart-полем
  `file`. Поддержаны JSON-массив, объект `{"items":[...]}`, NDJSON и ZIP с JSON-файлами;
  запись содержит `payload` и `employee_id` или `employee_number`. Preview не пишет в БД,
  commit создаёт/ротирует токены. Отчёт: `rows_total`, `rows_ok`, `rows_error`,
  `rows[].line/status/reason`; лимиты — 5000 записей, 25 МБ файл, 200 JSON-файлов в ZIP.
- **Бумажные QR**: выдача на 1 месяц включительно по Asia/Novosibirsk, один активный токен
  на сотрудника (`409` при повторе), идемпотентный отзыв. Payload включает данные
  сотрудника, `token`, `type=paper`, `valid_from`, `valid_until`. Просроченный активный
  токен автоматически переводится в `expired` при попытке выдать новый.
- **Проверка QR**: `GET /qr/{token}` возвращает `valid`, `token_status`, `signature_valid`,
  `employee_id`, `qr_data_mismatch`; для неизвестного токена — `404` с
  `token_status=not_found`. Статус `expired` вычисляется по датам.
- **`qr_data_mismatch` в отметках**: `POST /mark` сравнивает известные поля payload с
  текущими данными сотрудника и сохраняет флаг в `marks.qr_data_mismatch`.
- **PDF/A**: `GET /admin/qr/paper/{id}/pdf` формирует PDF с QR-кодом, логотипом-надписью,
  данными сотрудника, сроком, инструкцией и телефоном поддержки; встроены Unicode-шрифты
  DejaVu, добавлены XMP-метаданные PDF/A-1b. Отозванный/истёкший токен помечается в форме.
- **API-ответы**: `QrToken` дополнен `payload` и `qr_content` (готовая JSON-строка для
  QR-кода с `token`, `signature`, `payload`). OpenAPI обновлён.
- **Аудит**: `qr.static_upload`, `qr.bulk_preview`, `qr.bulk_commit`, `qr.paper_issue`,
  `qr.paper_revoke`.
- **Зависимости**: `github.com/skip2/go-qrcode`, `github.com/go-pdf/fpdf v0.9.0`;
  шрифты DejaVu Sans/Bold включены через `go:embed`.

### Отклонения и решения

## Этап 12. Нагрузочное тестирование и оптимизация — ✅ ВЫПОЛНЕН (2026-10-19)

Задачи:
- Нагрузочный тест: 150 операторов, 60 отм/с, 30 минут.
- Проверка p95: запись ≤ 50 мс, ответ API ≤ 300 мс.
- PgBouncer, read-реплика для экспорта и веб-панели, асинхронная телеметрия.
- Партиционирование `marks` по месяцам (автогенерация партиций).
- Мониторинг p95 и алерты.

Факты:
- Инструмент `backend/cmd/loadtest` (150 воркеров, настраиваемые интенсивность/длительность,
  перцентили p50/p95/p99, коды ответов); транспорт клиента с большим пулом idle-соединений.
- `marks` партиционирована по месяцам; `create_marks_partition` вызывается планировщиком
  `internal/jobs` (предыдущий/текущий/следующие месяцы).
- Пул БД настраивается через `DB_MAX_CONNS` (по умолчанию 40) и `DB_MIN_CONNS` (4);
  `PgBouncer` `default_pool_size` — через `PGBOUNCER_POOL_SIZE` (40), режим transaction.
- Экспозиция метрик: `GET /metrics` (p50/p95/p99 и счётчики по маршрутам).
- Результат стабильного прогона 150 сотрудников × 60 отм/с × 60 с: 3542 запроса,
  0 ошибок, p50 174 мс, **p95 231 мс**, p99 287 мс (цель p95 ≤ 300 мс выполнена).
  При малой нагрузке (5 отм/с) p95 ≈ 19 мс. Единичный прогон давал p95 ≈ 828 мс
  (вероятно, autovacuum/холодный кэш) — вынесено как наблюдение.
- Read-реплика не разворачивалась (в compose нет реплики); отложено до production-этапа.

Результат: отчёт о нагрузочном тестировании, настройки производительности.

## Этап 15. Роли «руководитель смены / директор / кадры», отчёты, демо-база, импорт и мобильные сборки — ✅ ВЫПОЛНЕН (2026-10-19)

- Отчёты по сменам, отметкам и сводка `по сотруднику`/`по группе сотрудников`
  (`employee_id`/`employee_ids`, фильтр `position`) с выгрузкой в табличный CSV.

- Демонстрационная база на 10 сотрудников с кнопками загрузки/очистки
  (`POST /admin/demo/seed`, `POST /admin/demo/clear`).
- Папка шаблонов загрузки данных `templates/` (сотрудники, графики, офлайн-отметки,

- Загрузка мобильных приложений (.apk/.ipa) из панели администратора
  (`POST /admin/mobile-builds`) и публичное скачивание (`GET /mobile-builds/{id}/download`).

- Backend: `internal/repo/{users,reports,mobile,demo}.go`,
  `internal/httpapi/{admin_users,admin_employees_import,admin_demo,reports,mobile_builds}.go`;
  маршруты зарегистрированы в `internal/httpapi/server.go`. Диапазон отчётов
  ограничивается middleware `reportsRole` (роли `admin`, `shift_lead`, `director`, `hr`).

  сотрудников `DEMO-0001…DEMO-0010`, графики `custom 1-5 09:00-18:00` и закрытые
  смены с отметками за последние 3 недели. `ClearDemo` удаляет только демо-данные
  в порядке `marks → shifts → mark_idempotency → employees`.
- Frontend: новое приложение `reports-web` (логин, фильтры периода/должности/табельных
  номеров, вкладки «Смены/Отметки/Сводка», кнопка выгрузки CSV); в `web-admin`
  добавлены разделы «Импорт сотрудников», «Создать пользователя», «Мобильное
  приложение», «Демо-данные», «Шаблоны».
- Подтверждение: `TestStage15E2E` (создание роли, доступ к отчётам и CSV, запрет для
  рядового сотрудника, preview/commit импорта, seed/clear демо, upload/list/download/delete
  сборки); весь `go test ./...` — зелёный.

Отклонения:
- Прямая привязка `employee_id` разрешена только для ролей `employee`/`operator`.
- `reports-web` слушает порт 8083 (`REPORTS_PORT`).
- Сборки мобильного приложения загружаются как `.apk`/`.ipa` (сборка самих приложений —
  Этапы 7–9).

Результат: роли, отчёты, демо-база, импорт сотрудников, шаблоны и раздача мобильных
сборок реализованы и проверены.
